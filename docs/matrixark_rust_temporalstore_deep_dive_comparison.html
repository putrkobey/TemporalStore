Executive Summary

Rust TemporalStore is no longer just a client or proxy shell. The core runtime has a real storage engine made of TemporalEngine, slot-first indexes, page/block address aliases, packed timestamp pages, a write-ahead log, a multi-layer cache, storage lifecycle reports, and data-node schedulers. MatrixArk context records are stored on the same engine primitives as other data models: model maps point to PageAddress values, timestamped maps point to packed pages, and context-specific retrieval uses engine commands plus workflow code.

The deepest Rust storage engine code currently lives in crates/temporalstore-rust/src/engine.rs, engine/engine_storage_state.rs, engine/engine_context.rs, engine/packed_pages.rs, block_store.rs, cache.rs, wal.rs, and data_node.rs.

The engine remains the mature reference for tightly packed page indexes, coroutine-driven StorageManager, page GC, page compaction, zones, stream/blob rollover, and production path behavior. Rust has caught up on public contract shape and much of the runtime machinery, but it still carries more report scaffolding and compatibility aliases, and its page/block layer is less compact than the packed structures.

Rust Storage Model

1. Engine owns loaded shards

TemporalEngine stores loaded shard state in Arc<RwLock<HashMap<ShardId, ShardState>>>. A command first resolves the shard, validates admission and readonly state, then executes against the in-memory model maps and page store.

2. Model maps point to pages

ShardState keeps maps such as strings, hashes, sets, features, sequences, control state, and context records. Most values are not stored inline; they point to PageAddress, which is currently an alias for BlockAddress.

3. Slot index is the runtime authority

CoreIndex contains a SlotMap. Each SlotNode records object ids, deleted object ids, dirty generation, in-memory/loading flags, TTL, and a PageIndexMap. The shape mirrors the Index -> SlotMap -> SlotNode -> PageIndex/ObjectIndex hierarchy, but uses Rust maps rather than packed structs.

4. Pages are durable segments

LocalBlockStore appends encoded page records and returns BlockAddress. The public page-store compatibility module reexports BlockAddress as PageAddress and LocalBlockStore as LocalPageStore, so newer code can use canonical block names while older engine code still compiles with page-store terms.

Write And Read Paths

Rust write path

ExecuteRequest
  -> TemporalEngine::execute_with_storage_override
  -> shard lookup and admission
  -> validate command preconditions
  -> execute_on_shard(cache, page_store, async_storage, command)
  -> append value/page through LocalPageStore alias
  -> update model map and slot-first index
  -> mark dirty_objects
  -> if sync durable:
       wal_store.append(command)
       index_log_store.append_json(serialized ShardState)
       persist index bytes

In Rust, the loaded ShardState is both the current logical object index and the source for rebuilding secondary views. The promote_model_maps_to_slot_index_authority and reconcile_secondary_views_from_slot_index calls keep the slot-first index and model maps aligned.

Rust read path

Command query
  -> model map lookup or slot_index_page_address
  -> PageAddress / BlockAddress
  -> read_page_bytes(cache, page_store, shard_id, address)
  -> MultiLayerCache get/refill or LocalBlockStore read
  -> decode bytes into object, feature point, or ContextWire value
  -> filter by timestamp/status/kind/score where needed

Timestamped models use BTreeMap<u64, PageAddress>. For packed timestamp pages, several logical timestamps can point to the same durable page. read_feature_point_cached keeps a per-query decoded page cache so repeated reads from the same packed page avoid repeated JSON decode.

Cold scan path

Cold timestamp/page range
  -> page index scan
  -> no-cache page read
  -> bounded decode
  -> no hot-cache promotion

The canonical cold-scan contract is defined in engine/engine_reports.rs and exposed through storage_cold_scan_contract. The Rust runtime has the TS_COLD_SCAN_NO_CACHE_FILL knob and report fields such as cold_scan_no_cache_reads and hot_cache_promotions. The intended production invariant is that temporal compression or GC scans do not warm serving cache unless a user-facing retrieval explicitly asks for raw evidence.

Multi-Layer Cache

Rust's MultiLayerCache is a real tiered cache, not just a map. It contains memory and pmem maps, an SSD/disk index, pin tracking, an access order, async writeback queue, admission metadata, and detailed stats.
